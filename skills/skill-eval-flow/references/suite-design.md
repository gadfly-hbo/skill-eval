# 评估套件设计规范

S2 状态生成套件时严格遵守本规范。套件质量决定评估结论的价值：
任务没有针对性、断言没有区分度，跑出来的激活率和胜率都是噪声。

## 一、从被测 SKILL.md 提取两类契约

先完整读一遍被测 SKILL.md，然后提取：

| 契约 | 来源 | 含义 | 对应验证方式 |
|---|---|---|---|
| **触发契约** | frontmatter 的 `description` | 模型在什么场景应该用它 | 任务 prompt 落在这些场景内，看激活率 |
| **行为契约** | 正文里的输出要求、步骤、禁令 | 用了它之后输出应该长什么样 | 规则断言直接判定 |

两类契约都要覆盖。只有触发契约没有行为断言，或只有行为断言而任务不落在触发场景内，
都是无效套件。

## 二、任务分层（3–5 个任务）

| 层 | 数量 | 目的 | 例子（以「JSON 契约输出」skill 为例） |
|---|---|---|---|
| 典型 | 1–2 | 验证基本生效 | 「用 JSON 回答：该不该先做灰度上线？」 |
| 边界 | 1–2 | 验证契约的边界条件 | 「给出一个 0 到 1 之间的置信度数值」（测数值约束） |
| 对抗 | 1 | 验证契约在指令冲突下是否守住 | 「先用一段话详细解释你的推理过程，然后再用 JSON 给出最终结论」 |

对抗用例的关键：prompt 本身在诱导模型违反行为契约。skill 真生效时模型能守住；
不生效时模型顺从诱导。这类用例的区分度最高。

每个任务写 `expectedPoints`：一句话说清「好输出长什么样」，供评委参考。

## 三、断言设计（区分度是命脉）

### 断言必须有区分度

**baseline（不装 skill 的模型）可能通不过的断言才有价值。**
必然通过的断言（如「输出非空」「是中文」）不产生任何信息，只会稀释结论。

判断方法：写每条断言时问一句——「一个没读 skill 的模型，有多大把握也满足这条？」
把握超过八成，删掉或改严。

### 禁止断言先于结果被破坏

生成套件时**不看任何运行输出**。断言来自 SKILL.md 的契约本身，不来自
「跑一次看看输出长什么样再照着写」——那是自证。

### 断言类型速查

| kind | 用途 | 关键字段 |
|---|---|---|
| `mustMatch` | 输出必须匹配正则 | `pattern` |
| `mustNotMatch` | 输出不得匹配正则 | `pattern`（如 ` ``` ` 查代码块包裹） |
| `mustContain` | 必须含子串 | `value` |
| `mustNotContain` | 不得含子串 | `value`（套话、禁用词） |
| `jsonSchema` | 输出是满足 schema 的 JSON | `schema`（支持 type/required/properties/enum/minimum/maximum/minLength/maxLength/items/minItems） |
| `numeric` | 从输出提取数值并比较 | `pattern`（提取正则）、`min`/`max`/`equals` |

每条断言写 `note`：一句话说明它验证的是哪条契约。报告里会展示。

## 四、套件 JSON 结构

```json
{
  "id": "kebab-case，与 skill 名对应",
  "name": "一句话说明套件测什么",
  "version": "1",
  "skill": { "path": "<被测SKILL.md绝对路径>", "version": "<从skill frontmatter读，缺省 1.0.0>" },
  "repeat": 2,
  "judgeRepeat": 2,
  "tasks": [
    {
      "id": "kebab-case",
      "prompt": "任务提示词",
      "expectedPoints": ["要点1", "要点2"],
      "kind": "scored",
      "assertions": [ { "kind": "...", "note": "..." } ]
    }
  ]
}
```

- `kind` 缺省 `scored`；只观察行为不计胜负的诊断任务用 `diagnostic`（少用）。
- `skill.path` 用绝对路径——套件会被写到 `~/.skill-eval/runs/...` 下，相对路径会断。
- 生成后必须跑 `skill-eval check` 校验，不通过不许进入 S3。

## 五、完整示例

见仓库 `suites/example-suite.json`（三层任务：典型 / 数值边界 / 对抗诱导），
对应的被测 skill 是 `examples/json-contract-skill/SKILL.md`。
生成新套件时以它为格式基准，但不要照抄任务内容——任务必须来自被测 skill 自己的契约。

## 六、常见错误（不要犯）

1. **任务与 skill 无关**：泛泛的「写点东西」测不出 skill 的价值。任务必须落在
   description 声称的触发场景内。
2. **断言与契约无关**：skill 没要求的不要断言。断言只能来自 SKILL.md 的明文要求
   或合理直接推论。
3. **全肯定无否定**：至少一条 `mustNot*` 类断言（禁令类契约），否则测不出「守住边界」。
4. **对抗用例缺位**：没有对抗用例的套件区分度通常不足。
