# 评估套件设计规范

S2 状态生成套件时严格遵守本规范。套件质量决定评估结论的价值：
任务没有针对性、断言没有区分度，跑出来的激活率和胜率都是噪声。

## 一、从被测 SKILL.md 提取两类契约

先完整读一遍被测 SKILL.md，然后提取：

| 契约 | 来源 | 含义 | 对应验证方式 |
|---|---|---|---|
| **触发契约** | frontmatter 的 `description` | 模型在什么场景应该用它 | 任务 prompt 落在这些场景内，看激活率 |
| **行为契约** | 正文里的输出要求、步骤、禁令 | 用了它之后输出应该长什么样 | 规则断言直接判定 |

两类契约都要覆盖。只有触发契约没有行为断言，或只有行为断言而任务不落在触发场景内，
都是无效套件。

## 二、任务分层（4–6 个任务）

| 层 | 数量 | 目的 | 例子（以「JSON 契约输出」skill 为例） |
|---|---|---|---|
| 典型 | 1–2 | 验证基本生效 | 「用 JSON 回答：该不该先做灰度上线？」 |
| 边界 | 1–2 | 验证契约的边界条件 | 「给出一个 0 到 1 之间的置信度数值」（测数值约束） |
| 对抗 | 1 | 验证契约在指令冲突下是否守住 | 「先用一段话详细解释你的推理过程，然后再用 JSON 给出最终结论」 |
| 负向误触发 | 1 | 验证无关任务不乱触发（`shouldActivate: false`, `kind: "diagnostic"`） | 「帮我润色这段周报的语气」 |

对抗用例的关键：prompt 本身在诱导模型违反行为契约。skill 真生效时模型能守住；
不生效时模型顺从诱导。这类用例的区分度最高。

每个任务写 `expectedPoints`：一句话说清「好输出长什么样」，供评委参考。

## 三、断言设计（区分度是命脉）

### 断言必须有区分度

**baseline（不装 skill 的模型）可能通不过的断言才有价值。**
必然通过的断言（如「输出非空」「是中文」）不产生任何信息，只会稀释结论。

判断方法：写每条断言时问一句——「一个没读 skill 的模型，有多大把握也满足这条？」
把握超过八成，删掉或改严。

### 禁止断言先于结果被破坏

生成套件时**不看任何运行输出**。断言来自 SKILL.md 的契约本身，不来自
「跑一次看看输出长什么样再照着写」——那是自证。

> **二次测评例外**：复评同一个 skill 时，允许参考**上一轮的失败断言**来放宽过严的断言——
> 这不是自证，因为断言仍然来自契约，放宽的依据是「skill 自己规定了另一种合规写法」。
> 但放宽后**必须重跑判别力校验**（见下节）。

### 断言只锚契约语义，不绑词形

中文报告的标点宽度（全角 `（）` vs ASCII `()`）、字段名、表格表头措辞都是**风格不是契约**。
把断言绑死在某种写法上，会把**真实合规**的输出判成 FAIL——这是「假失败」的主要来源。

反例（实测）：断言要求出现「待确认」，而 skill 写的是「**未做体检项**：客流与销售额是否同口径
（含税/含退货…）」——语义满足、词形不匹配 → 假失败。

修法：断言接受**skill 自己规定的所有合规措辞**，而不是某一个词形。

> **但放宽不得牺牲判别力**：放宽后必须复验「baseline 仍不命中」。
> 反例：把「统计期间」放宽到匹配 `2026-03` 会丧失判别力——实测 baseline 两次输出同样含 `2026-03`。
> 正确做法是锚定「口径声明的**结构性证据**」（如「仅有…单月」「目前只有…2026-03」）而非裸日期。

### 用 `equivalentPatterns` 声明等价写法（让工具能识别假失败）

**「断言过严」与「skill 真缺陷」在布尔数据里完全无法区分**——
实测两条假失败与一条真缺陷的逐次签名都是 `baseline ✗✗ / skill ✓✗`。
区别只在输出文本里：假失败命中了 skill 契约允许的其他写法，真缺陷连痕迹都没有。

所以要让工具能区分，必须**由断言显式声明** skill 契约里允许的其他写法：

```json
{
  "kind": "mustMatch",
  "pattern": "责任人|负责人|\\|\\s*谁(?:做|负责)?\\s*\\|",
  "equivalentPatterns": ["谁做", "谁负责"],
  "note": "红线 5：建议必须落到责任人"
}
```

判定规则（`src/core/improve.ts`）：

| 情况 | 判定 |
|---|---|
| 失败且命中了某个 `equivalentPatterns` | **断言过严**（假失败）→ 要改套件，不是 skill |
| 失败且等价写法都没命中 | 真缺陷 → 要改 skill |
| 失败但没声明 `equivalentPatterns` | 无法区分 → 按原逻辑归类 |

`equivalentPatterns` 是**兜底**——`pattern` 放宽后它就不再是必需的；
但保留它能让「pattern 漏了某种措辞」被识别成假失败而不是误判成 skill 缺陷。

### 断言方向不得与 skill 契约冲突

写断言前先确认：**skill 有没有明确允许另一种写法？** 有就不能用 `mustMatch` 强制它自己的那一种。

实测：skill 明文写着「宁可写『本期天数仅为基期的 53.6%…』，也不要写可能算错的等式」，
而断言用 `mustMatch` 强制「必须出现 46.4」——**断言方向与 skill 契约相冲突**。
修法：改为 `mustNotMatch`（禁错等式），或放宽为「46.4 或合规的 53.6 叙述式」。

### 必须把 skill 自带的门禁脚本纳入断言

被测 skill 若自带可执行门禁（`quality_check.py` / `validator` / `lint` / `checklist`），
**那是信噪比最高的检查面，必须纳入断言**：

- 断言套件和评委都是在**猜**契约
- 门禁脚本是 **skill 作者自己写的契约实现**——措辞以它为准，不会出现词形错位

实测（data-analysis）：断言套件和评委**都没抓到**「直答形态未声明输出形态」这个缺陷，
只有跑 `scripts/quality_check.py` 才暴露（baseline 0/10 通过、skill 6/10 通过，失败全是同一根因）。
把门禁的匹配规则（如 `RE_DIRECT_MODE`）翻译成断言后，该断言判别力极强
（baseline 10/10 全不命中，skill 侧 9/10 不命中）。

### 断言类型速查

| kind | 用途 | 关键字段 |
|---|---|---|
| `mustMatch` | 输出必须匹配正则 | `pattern` |
| `mustNotMatch` | 输出不得匹配正则 | `pattern`（如 ` ``` ` 查代码块包裹） |
| `mustContain` | 必须含子串 | `value` |
| `mustNotContain` | 不得含子串 | `value`（套话、禁用词） |
| `jsonSchema` | 输出是满足 schema 的 JSON | `schema`（支持 type/required/properties/enum/minimum/maximum/minLength/maxLength/items/minItems） |
| `numeric` | 从输出提取数值并比较 | `pattern`（提取正则）、`min`/`max`/`equals` |

每条断言写 `note`：一句话说明它验证的是哪条契约。报告里会展示。

## 四、套件 JSON 结构

```json
{
  "id": "kebab-case，与 skill 名对应",
  "name": "一句话说明套件测什么",
  "version": "1",
  "skill": { "path": "<被测SKILL.md绝对路径>", "version": "<从skill frontmatter读，缺省 1.0.0>" },
  "repeat": 3,
  "judgeRepeat": 2,
  "tasks": [
    {
      "id": "kebab-case",
      "prompt": "任务提示词",
      "expectedPoints": ["要点1", "要点2"],
      "kind": "scored",
      "shouldActivate": true,
      "assertions": [ { "kind": "...", "note": "..." } ]
    }
  ]
}
```

- `kind` 缺省 `scored`；只观察行为不计胜负的诊断任务用 `diagnostic`（少用）。
- `skill.path` 用绝对路径——套件会被写到 `~/.skill-eval/runs/...` 下，相对路径会断。
- 生成后必须跑 `skill-eval check` 校验，不通过不许进入 S3。

## 五、完整示例

见仓库 `suites/example-suite.json`（三层任务：典型 / 数值边界 / 对抗诱导），
对应的被测 skill 是 `examples/json-contract-skill/SKILL.md`。
生成新套件时以它为格式基准，但不要照抄任务内容——任务必须来自被测 skill 自己的契约。

## 六、常见错误（不要犯）

1. **任务与 skill 无关**：泛泛的「写点东西」测不出 skill 的价值。任务必须落在
   description 声称的触发场景内。
2. **断言与契约无关**：skill 没要求的不要断言。断言只能来自 SKILL.md 的明文要求
   或合理直接推论。
3. **全肯定无否定**：至少一条 `mustNot*` 类断言（禁令类契约），否则测不出「守住边界」。
4. **对抗用例缺位**：没有对抗用例的套件区分度通常不足。
