# skill-eval-flow — Skill 评估状态机

编排 `skill-eval` CLI，把「评估一个 SKILL.md」跑成一个五状态工作流。
本 skill 只做编排：确定性检查交给脚本，实验执行交给 CLI，AI 判断只出现在两处——
生成套件（S2）与解读报告（S4）。

## 选择运行方式

- **评估具体 Skill**。使用已固化的 `skill-eval` 入口，进入 S0，定位候选并收集档位和消融选择。
- **验证评估器链路**。仅在用户单独授权实际冒烟时运行 `npm run smoke`。公开诊断题复用 `eval`，两侧各一次、匿名评委一轮，共 3 个会话。检查 `REPORT.md` 和 `execution-status.json` 的会话、激活、内容、格式、评委及 usage 记录后返回结果。

### 正式测评边界

两侧执行同一份冻结计划，使用同样的题集、模型、轮数和判据。正式分数与判定以固化版本生成的报告为准。Qoder 只评价被测 Skill，核对原始证据是为了确认候选问题和给出修改建议。正式测评中不得质疑或修改测评器、替换冻结判据、另行计分或自行重跑。测评器复盘和升级单独授权。

Qoder 对候选文件的直接操作限于静态审阅，包括候选自带的检查脚本。候选侧 Agent 在 `skill-eval eval` 的受控会话内自主使用工具。

执行受阻时保留已有产物，原样报告命令退出状态、错误和证据路径。缺失或失败记录按工具给出的状态交付，候选问题仅按已核实的证据归因。

## 用户怎么用

1. 把待测 skill 的**整个文件夹**放进待测评区 `<仓库>/pending/`
2. 调用本 skill：`/skill:skill-eval-flow` 或说「评估这个 skill」
3. 一次回复档位和消融选择，例如「中，不增加」

## 环境适配（先读）

本 skill 遵循 Agent Skills 规范，可被任何实现了该规范的 agent 加载。
指令中出现的宿主能力名按以下规则降级：

| 指令中的能力 | WorkBuddy | 其他 agent |
|---|---|---|
| 询问用户 | `AskUserQuestion` 工具 | Qoder 等宿主有同类工具时复用，否则直接用自然语言提问 |
| 后台执行长命令 | `run_in_background` | 前台执行并等待，按已完成会话报告进度 |
| 呈现报告文件 | `present_files` | 在回复中给出报告文件的绝对路径 |

不确定宿主是否支持某能力时，选降级方案，不要因为工具不存在而中断流程。

## 全局规则（任何状态都必须遵守）

1. **失败即数据**：单次运行失败、超时、空输出都计入分母，禁止选择性重跑。
2. **失败要留痕**：任何状态失败都保留已有产物，把报错原文呈现给用户，不静默吞掉。
3. **断言先于结果**：生成套件时不看任何运行输出，避免自证。
4. **真实运行**：所有结论必须来自真实模型调用，不用静态检查或回放冒充。

## 正式测评参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| 被评模型 | `minimax-cn/MiniMax-M3.1-Flash` | 使用真实入口支持的精确模型身份 |
| 评委模型 | `xiaomi-token-plan-cn/mimo-v2.6-flash` | 与被评模型不同 provider，避免自我偏好 |
| pi 隔离 HOME | `~/.skill-eval/pi-home` | preflight 会自动准备 |
| 运行目录 | `~/.skill-eval/runs/<YYYYMMDD-HHmmss>-<skill名>/` | 套件、产物、报告都在这里 |
| 归档仓库 | 评估所在项目的 git 仓库根目录 | 通过 `skills/` + `package.json` 探测，也可用 `--repo` 指定 |
| 归档根目录 | `<仓库>/archive/` | 必须在 `skills/` 之外，否则会被 agent 自动扫描 |
| 待测评区 | `<仓库>/pending/` | **常驻投放入口**：未测 skill 放这里（可直接拖入），通过后从暂存区移出，暂存区本身保留 |

## S0 收集输入

### 0.1 定位被测 skill

按优先级找：

1. **用户消息里给了路径** → 用它
2. **待测评区里有且只有一个 skill** → 直接用它
3. **待测评区里有多个 skill** → 列出清单，问用户要评哪个（用 AskUserQuestion）
4. **待测评区为空** → 告诉用户把 skill 文件夹放进 `<仓库>/pending/`，并给出该目录的绝对路径，然后终止

查待测评区：

```bash
skill-eval pending --json
```

输出是 JSON，`skills[].skillPath` 就是待测 SKILL.md 的绝对路径。
**一个待测 skill 都没有时不要编造路径**——那是把「没找到」伪装成「找到了」。

> **不用指定 `--repo`**——CLI 会依次尝试：环境变量 `SKILL_EVAL_REPO` →
> 当前目录向上探测 → 从 skill-eval 自身安装位置反推。
> 你的 cwd 通常是会话工作区而不是 skill-eval 仓库，但待测评区就在 skill-eval 仓库里，
> 第三层兜底能保证找得到。
>
> 评估**其他项目**的 skill 时，才需要显式 `--repo <那个项目的仓库>`。

### 0.2 选择档位和消融

定位候选后，展示下表并在同一轮收集两项独立的单选。两项均缺失时，支持多题的 `AskUserQuestion` 使用两个问题对象：

```json
{
  "questions": [
    {
      "header": "测评档位",
      "question": "选择测评档位",
      "options": [
        {"label": "高", "description": "扩大独立场景覆盖，检查评委换位"},
        {"label": "中", "description": "推荐用于日常测评"},
        {"label": "低", "description": "快速看实际激活和输出"}
      ]
    },
    {
      "header": "消融",
      "question": "是否增加消融",
      "options": [
        {"label": "增加", "description": "追加一组同规模的阴性对照"},
        {"label": "不增加", "description": "只运行原版对照"}
      ]
    }
  ]
}
```

宿主只能提供单题时，用一条普通消息分别列出「测评档位（高 / 中 / 低）」和「消融（增加 / 不增加）」，请用户一次回复。档位与消融独立组合，六种组合均可选择。

| 档位 | 总题数 | 每题每侧次数 | 每对评委轮数 | 不增加消融 | 增加消融 | 用途 |
|---|---:|---:|---:|---:|---:|---|
| 低 | 3 | 1 | 1 | 9 | 18 | 快速看实际激活和输出 |
| 中（推荐） | 5 | 2 | 1 | 30 | 60 | 日常测评，观察同题稳定性 |
| 高 | 16 | 2 | 2 | 128 | 256 | 扩大独立场景覆盖，检查评委换位 |

总题数包含诊断题。会话数是计划规模，正式结论仍按原有证据门槛判定。用户可回复「中，不增加」，也可以在发起时一并指定。沿用已明确的答案，只补问缺项；两项齐备后进入 S1。仅要求方案或离线检查时，止于所请求的范围。

如果用户明确给出自定义规模或指定按原方案复测，按该计划收集题数和轮次，仍明确本轮消融选择。档位与用户指定的冻结方案冲突时，请用户决定采用哪份计划。

## S1 环境自检

执行 `scripts/preflight.sh`（相对本 skill 目录）：

```bash
bash <本skill目录>/scripts/preflight.sh
```

脚本检查：node ≥ 22、`skill-eval` 在 PATH、`pi` 可用、pi 隔离 HOME 就绪
（缺失时自动创建并从 `~/.pi/agent/` 复制认证文件、清理残留 `*.lock` 目录）。

- 退出码 0 → 进入 S2。
- 退出码非 0 → 保留退出码和报错原文，报告本次执行受阻并终止。
- pi 未认证（`~/.pi/agent/auth.json` 不存在）不可自动修复：提示用户先运行一次 pi 完成认证，终止。

## S2 套件就绪

分两路：

- **用户指定套件或冻结计划** → 使用指定的套件。若计划已记录版本和哈希，逐项核对一致后执行 `skill-eval check --suite <路径>`。
- **复用或生成套件** → 按下文检查已有套件。需要出题时，先读 `references/suite-design.md`，从被测 SKILL.md 提取契约，按选定题数准备套件并校验。

```bash
skill-eval check --suite <已选套件路径>
```

已选的现有套件校验不通过 → 保留错误并停止。仅在为新计划首次拟题、尚未冻结时，可按校验结果修订该草案。

> ⚠️ **套件不要放进运行目录**。运行目录是模型的 cwd（`<运行目录>/cases/...`），
> 模型会 `find` 向上摸到运行目录；若里面有 `suite.json`（内含 `skill.path` 绝对路径），
> baseline 侧就会顺着路径读到被测 skill 全文——**对照实验的唯一变量被破坏，增益被系统性压低**。
> 套件放仓库 `suites/` 目录，`--suite` 直接指过去。

### 二次测评：优先复用仓库里已有的套件

**同一计划复评时复用原冻结版本和哈希**，使结果变化可归因到 skill 改动。题数或判据变化时，作为新计划保留独立的套件和记录。跨套件版本结果单列，候选纵向对比仅使用相同冻结套件。

查仓库 `suites/` 下有没有现成的：

```bash
ls <仓库>/suites/
```

- **有** `<skill名>-vN.json` → 未指定套件的新计划，先筛出与候选路径及题数相符的版本，再按整数 `N` 选择最高版本。`decision-review` 的 v1/v2/v3/v4 同时匹配时，新计划选 v4。没有匹配版本时另存新套件，保留旧套件供复核。新增题目必须覆盖独立场景。
- **没有** → 按规范生成，并存档到 `<仓库>/suites/<skill名>-v1.json`，
  下次复评直接复用。

已有题集保留原版本和哈希。新计划的独立草案在看到任何运行输出前完成校验与冻结。

### 判据冻结纪律

两侧采用同一冻结判据。新草案的诊断题用离线正反例检查正确性，两侧答对均应通过。套件冻结后，其规则和分母贯穿计分、报告及候选改版复测。

### G1 冻结执行范围

校验通过后，记录档位或自定义方案、套件、候选、模型、两项轮数、消融选择和预计费用。按冻结配置显式传入 `--repeat` 和 `--judge-repeat`。每组完整计划为 `任务数 × repeat × (2 + judgeRepeat)` 个会话，包含诊断题。消融增加一组同规模会话。会话内原生工具调用和自纠的 HTTP 请求另计。

用户已授权真实运行且范围明确时，直接进入 S3。用户要求先看方案，或缺少会影响范围和费用的选择时，先补齐所需信息。

## S3 对照评估

```bash
skill-eval eval \
  --suite <仓库>/suites/<skill名>-v*.json \
  --skill <被测SKILL.md绝对路径> \
  --model <被评模型> \
  --judge-model <评委模型> \
  --home ~/.skill-eval/pi-home \
  --repeat <n> --judge-repeat <n> \
  --out <运行目录>
```

用户要求直接入库且本轮关闭消融时，可传 `--archive-to <项目仓库路径>`。已选消融时，先按文末流程取得阴性对照核验状态，再进入 S4。需要归档时遵循 S5。

后台执行并等待完成（WorkBuddy 用 run_in_background；其他 agent 前台等待即可），
把 CLI 的进度输出（`[run]`/`[judge]` 行）精简转述给用户。完成后进入 S4。

> ⚠️ **跑批前必须确保运行目录是干净的**——不要把 `suite.json` 复制进去。
> 模型 cwd 在运行目录里，会 `find` 到 `suite.json` 并顺着 `skill.path` 读到被测 skill，
> 污染 baseline 侧（工具会自动检测并在报告首屏告警，但重跑代价更高）。
> 正确做法：`--suite` 直接指仓库 `suites/` 里的文件，运行目录只放产物。

命令结束后核对运行目录和 `execution-status.json`。未产生执行记录时按执行受阻交付，保留退出码和实际输出。

## S4 解读报告

1. 读 `<运行目录>/REPORT.md` 与 `summary.json`。
2. 呈现 `REPORT.md`（WorkBuddy 用 present_files；其他 agent 在回复中给出绝对路径）。这是最终交付物。
3. 给用户一段不超过 15 行的解读，包含：
   - verdict（有效 / 无效 / 结论不足）及含义
   - 正向激活和负向误触发，各列命中数/相应的运行数。全组运行数单列
   - 从正式报告或 `summary.json` 取原始评委胜率（`winRate`，已归一到候选侧）和规则纠偏胜率（`ruleAdjustedWinRate`）。两者分母均为已判计分对（`scoredJudged`），诊断对单列
   - 任务等权配对增益及区间。若另列断言条目通过率，写明通过数/条目数及计分或诊断范围。断言全过率按运行数计算，单列有断言的成功运行数和全过数
   - 分别报告标签冲突轮数、规则与评委的配对分歧数、从胜率分子移除的评委胜出数，保留正式判定
   - 已选消融时，另列 `verify` 的正式状态、原因和证据路径。落盘产物的补充诊断单列
   - 下一步建议仅针对证据已确认的候选问题。运行受阻或证据不足时，保留正式状态与记录

报告缺失时呈现 `summary.json` 与 cases 目录并说明异常，不伪造结论。

### 评委标签与 A/B 换位

`rawVerdict` 只表示匿名展示时 B 相对 A 的结果。`swapped` 表示展示换位，标签随角色映射翻转，平局保持不变。例如 `rawVerdict: "win"`、`swapped: true`、`verdict: "loss"`、`labelConflict: null` 表示 baseline 胜出，未发生标签冲突。胜率直接引用已经归一的正式结果。

仅将 `pairwise[].judgeRuns[]` 中非空的 `labelConflict` 计作标签冲突。存在冲突时引用报告「评委标签纠正记录」的轮次、纠正方向及分差。普通换位与规则纠偏各有独立口径。

报告第 6 节的配对分歧是规则断言和评委方向不同的记录。规则纠偏只从计分对的胜率分子移除规则不支持的评委胜出，保留原始评委结果及全部分歧。举例来说，分歧 7 处、从 2/8 降到 0/8 时，报告 7 处分歧和 2 次移除，分别列数。

### 未通过时必须传达优化建议

正式判定未达有效门槛时，从报告的「优化建议」定位待核实项，再核对冻结断言、实际评分正文和候选约束。只有证据确认候选违反要求时，才给 Skill 改写建议。

- **候选约束**。确认 Skill 需要修改时，在最终解读给出可直接转交 OptraCall 的改写结论，写清失败证据、修改的文件或段落、改成什么行为、用哪条断言或用例验收。正向激活不足时核对触发证据。负向诊断题只有实际读取才判为误触发。
- **交付形态**。冻结用例指定文件时，核对其相对路径和 `deliverable.md` 评分副本，否则核对 `output.md`。引用状态行的实际位置及冻结要求，分别说明文件存在、位置合规和正文满足契约的证据。补充诊断单列输入、是否含诊断题和通过数/断言条目数。文件与对话的差异只支持交付差异，归因仍需候选违反冻结要求的证据。
- **待核实**。只有规则命中或自动分类时，保留为待核实项和正式判定。无已确认的候选问题时，说明目前缺少提出改写建议的证据。

## S5 归档（verdict 有效时）

有归档授权时，按以下门控处理候选快照。已选消融时先报告正式核验状态和证据限制，再按候选 verdict 及用户选择处理归档。补充诊断不作为放行依据。

### G2 门控（花钱后确认）

先看 verdict：

- `effective` → 继续归档
- `inconclusive` → 询问用户是否放行（放行会标记 `provisional=true`）；用户不明确就跳过归档
- `ineffective` → **不归档**，告知用户本轮未达有效门槛

用户在本轮明确说过「全自动」「不用问」时跳过 G2。

> 「结论不足」是**真实的不确定**，不是流程噪音——它意味着数据量不够支撑结论。
> 这种情况下问一句是合理的，因为「归档一个没测准的 skill」比「多问一句」代价更大。

### G3 增益门控（结论有效还不够）

按报告首屏的「任务等权配对增益」和冻结判据核对门槛。

- 增益 ≥ 10pp → 放行（10pp 来自阴性对照实验：原版 +50.0pp，契约剥离后 +8.6pp）
- 增益 < 10pp → 询问用户是否放行（放行会标记 `lowGain=true`）；用户不明确就跳过归档
- 增益不可判定（缺任一侧断言数据）→ 视为不达标，同样询问用户

### 执行归档

**方式一（推荐）**：在 S3 的 eval 命令里直接带 `--archive-to`，评估与归档一次完成。

```bash
skill-eval eval \
  --suite <仓库>/suites/<skill名>-v*.json \
  --skill <被测SKILL.md绝对路径> \
  --model <被评模型> \
  --judge-model <评委模型> \
  --home ~/.skill-eval/pi-home \
  --repeat <n> --judge-repeat <n> \
  --archive-to <项目仓库路径> \
  --out <运行目录>
```

**方式二**：评估已跑完、事后补归档。

```bash
skill-eval archive \
  --run <运行目录> \
  --skill <被测SKILL.md绝对路径> \
  --repo <项目仓库路径> \
  [--suite <套件id> --suite-version <版本> --skill-version <版本>]
```

两种方式走**同一套门控与写入逻辑**。`--run` 是归档的主入口——归档必须绑定
某一次评估的产物，只给 skill 路径无法确定对应的 verdict 与内容哈希。

CLI 自己也会把关：增益不达标时归档会被拒绝并提示 `--allow-low-gain`。
**不要为了让归档跑通就随手加这个参数**——先向用户确认增益是否可信。

### 归档后：从待测评区移出

项目仓库里维护一个**待测评暂存区**（默认 `<仓库>/pending/`）——
它是**常驻的投放入口**：未测评的 skill 放在那里当候选池，
测评通过后整个目录移入 `archive/`，**暂存区本身保留**（用户随时要往里放新的）。

**测评开始前**先把被测 skill 登记进暂存区：

```bash
skill-eval pending --repo <项目仓库路径> --skill <被测SKILL.md绝对路径>
```

如果用户是把 skill 文件夹**手动拖进**暂存区的，就不需要登记命令——
工具会自动识别（有 `SKILL.md` 就算一个 skill）并补写登记信息，来源标为「（手动投放）」。

**归档成功后** CLI 会自动把该 skill 从暂存区移出——不需要额外动作。
暂存区里剩下的都是没测过的，不该随归档一起走。

没通过测评的 skill 留在暂存区。按 S4 复核失败项并明确归属。

> 暂存区用 `--skill` 登记时存的是**副本**，源 skill 目录不受影响——源 skill 通常装在
> `~/.workbuddy/skills/` 下，那是被 agent 自动扫描的位置，不能因为登记就被搬走。
> 但用户**手动拖入**的是真实目录，移出时会连同该目录一起从暂存区删除
> （skill 本体已存进 `archive/`，不会丢）。

### 未通过 skill 的处理路径

```text
未通过 → 按 S4 核对失败项
       → 确认候选问题后交付 OptraCall 改写建议
       → 收到修订版并获得新运行授权后，按原冻结口径复测
```

二次测评必须**保持同一套件与模型**——否则无法把结果变化归因到 skill 改动上。

> 仓库路径用 `--repo` 显式指定；不指定时 CLI 会从当前目录向上探测含
> `skills/` + `package.json` 的目录，探测不到则归档到 `./archive`。

产出结构：

```
archive/<skill名>/
  <版本标识>/          # 版本标识 = <frontmatter版本>__<时间戳>
    SKILL.md           # skill 本体快照
    references/ scripts/   # 附属文件一并复制（缺了 skill 跑不起来）
    ARCHIVE.md         # 元信息卡：哈希、模型、结论、复现命令
    REPORT.md          # 评估报告副本，使归档目录自包含
  latest.json          # 当前版本指针
```

要点：

- **版本标识**默认取 frontmatter 的 `version` 字段 + 时间戳（如 `1.8.0__20261103-2303`）；
  frontmatter 没写版本则退化为纯时间戳
- **幂等**：内容哈希相同则跳过，不产生重复归档
- **不改原文件**：只读复制，绝不修改被测 skill
- **不自动 commit**：归档后把变更摘要告诉用户，由用户决定是否提交

归档完成后向用户汇报：归档路径、版本标识、内容哈希、复制文件数。

## 异常速查

| 症状 | 含义 | 处理 |
|---|---|---|
| 自检失败、命令无输出或报告缺失 | 执行证据不完整 | 保留退出码、实际输出和已有产物，按 S4 交付执行状态 |
| Provider 额度耗尽、会话失败或超时 | 本轮存在运行失败或未执行样本 | 原样列出状态及错误，保留执行清单和账本 |
| 报告首屏出现「对照实验污染告警」 | 报告记录了对照异常 | 原样引用告警与正式判定，保留全部样本 |
| verdict = 结论不足 | 正式证据或门槛尚未满足 | 引用结论摘要、覆盖率和未验证项，候选建议按 S4 |
| 归档被门禁拒绝 | 未达到归档条件 | 保留正式判定和拒绝理由，按 S5 处理 |
| 归档报「位于 skills/ 下」 | 归档目标会被 agent 自动扫描，污染后续评估 | 换 `--archive-root` 到仓库的 `archive/` 目录 |
| 归档后 git 里有大量二进制/大文件 | 被测 skill 含大体积附属文件 | 确认是否该入版本库；必要时在 `.gitignore` 排除特定子目录 |
| 待测评区 `pending/` 里仍有已测 Skill | 本轮未完成归档 | 保留原位置。改写建议与复测授权按 S4、S5 处理 |
| 待测评区 `pending/` 不存在 | 暂存区需要先建出来才能放 skill | 跑 `skill-eval pending --repo <仓库> --init` 建目录，或直接跑一次 `pending` 命令（会自动创建） |
| 待测评区被误提交进 git | 暂存区是本地投放入口，不是版本化资产 | 在 `.gitignore` 加 `pending/`；归档后的版本由 `archive/` 保管 |

## 阴性对照（用户选择消融时执行）

用户选择消融时执行阴性对照。它用于检查剥离行为契约后，原版的断言增益是否回落。

消融保留触发描述，剥离正文行为约束和附属文件。在冻结口径下，`verify` 同时核验候选与题集身份、配对覆盖、激活、增益和假阳性。增益回落只是其中一项条件。

**做法**：

1. 从原版运行清单指向的冻结 `SKILL.md` 生成剥离版，放在新的空目录，保留触发描述。
2. 保持同一套件、上下文、模型和两项轮数，用 `eval --skill <剥离版 SKILL.md>` 在新运行目录执行独立 baseline 与剥离版对照。
3. 用 `verify --json` 离线核验两份记录。保留 JSON 与退出码，并关联两个运行 ID。退出码为 1 时也要检查 JSON。

```bash
skill-eval verify --generate-broken <原版冻结SKILL.md> --out <破坏版目录>
# 对破坏版跑完同一套件后执行：
skill-eval verify --original <原版run-dir> --broken <破坏版run-dir> --json
```

按 JSON 的 `status` 交付正式消融结论。报告 `passed`（通过）、`failed`（未通过）或 `inconclusive`（证据不足），并引用 `reason`、两侧的任务等权增益与相关假阳性。无有效 JSON 时报告未核验和命令错误。正式 skill 结论与消融状态分别报告。

即使观察到增益回落，`failed`、`inconclusive` 或未核验时也要保留因果归因未证实的结论。正式状态与计分按冻结用例指定的评分载体交付，额外加入的材料单列为补充诊断。
