### 采纳

- **对照实验范式**：baseline（无 skill）vs variant（有 skill），同任务同模型成对运行。
- **成对评委（pairwise judge）**：不评绝对分，而评「variant 相对 baseline 是否更好」，输出 win/tie/loss + 双方 0-100 分 + 置信度。这比绝对打分稳定得多——绝对分在不同批次间漂移严重。
- **多轮评委多数票聚合**：judgeRepeat > 1 时按多数票聚合，保留全部单次判定。
- **评委提示词的反偏置约束**：明确写「不要因为 variant 使用了更多文字、格式更复杂或声称使用了 skill 就给高分」。
- **激活检测双证据**：输出关键词匹配 + 事件流路径匹配，两者结合才判定激活。
- **回归门禁严格接受**：candidate 必须严格优于 current，平局判 reject。
- **EFC 反馈效率**：用信息量/有效性/相关性/记忆四因子乘积衡量「一次运行换回多少有效信息」，用于同分时的次级排序。

### 改造

pi-xanthil 的实现与产品强耦合，本仓库做了以下剥离与改造：

| pi-xanthil 原实现 | 本仓库改造 | 原因 |
| --- | --- | --- |
| 依赖 `pi-adapter.ts` 内部 RPC 会话管理 | 改为独立的 `src/core/pi.ts`，直接 spawn `pi` CLI | pi-xanthil 的 adapter 与其 hooks/extensions/usage tracking 深度耦合，无法复用 |
| `evaluation-common.ts` 依赖 `cache.ts` 的 `trackWorkspaceUsage` | 只保留 metrics 采集，usage 直接落到运行产物 | 去掉产品数据库依赖 |
| 评分器是 `data-decision-agent-eval` 系列（业务语义） | 改为**规则断言 + 成对评委**双层 | 本仓库评的是 skill 行为约束，而非业务分析正确性 |
| 依赖产品 SQLite/Postgres 存历史 | 文件化 JSON 产物 + Markdown 报告 | 独立工具不应要求装数据库 |
| activation 用关键词模糊匹配 | 保留但**以工具调用取证为主**，关键词降级为辅助信号 | 见下节「实测发现」 |

### 实测发现（重要）

在 pi CLI v1.2.0 上实测验证：**skill 并非注入即生效**。

带 `--skill` 启动时，pi 只是把 skill 的 name/description/path 放进 system prompt 的 `<skills>` 段落；模型**必须主动调用 `read` 工具读取该文件**，内容才真正进入上下文。

实测事件流证据：

```
{"type":"message_end", ... "content":[{"type":"thinking","thinking":"There's a skill \"json-only-output\" matching. Let me read it."},{"type":"toolCall","name":"read","arguments":{"path":"/tmp/pi-probe/probe-skill.md"}}]}
{"type":"tool_execution_start","toolName":"read","args":{"path":"/tmp/pi-probe/probe-skill.md"}}
{"type":"tool_execution_end","toolName":"read","result":{...}}
```

这带来两个结论：

1. **激活检测必须以工具调用取证为主**。只看输出关键词会把「skill 根本没被读但回答里碰巧出现关键词」误判为激活。
2. **「skill 声明了但模型不读」是真实的失败模式**，必须能独立观测到。pi-xanthil 的关键词优先策略在这里会漏掉这类失败。

因此本仓库的激活判定改为：

- `tool_call`（强证据）：事件流中读到了目标 skill 路径 → 判定激活
- `output_keyword`（弱证据）：输出中出现 skill 关键词但无工具取证 → 判定为**弱激活**，单独统计，不计入激活率分子
- 两类都无 → 未激活

### 本仓库在移植中修正的问题

移植过程不是照搬。实测运行暴露了 pi-xanthil 实现中的几处问题，一并修正：

| 问题 | pi-xanthil 行为 | 本仓库修正 | 影响 |
| --- | --- | --- | --- |
| **评委轮次计票** | `reversed` 与 `flipped` 是同一次评委输出的两种解读，却被当成两票计入多数票聚合 | `reversed` 轮**只用于位置偏好探测**，不参与主判定聚合 | 避免人为放大票权，且把「位置偏差」与「质量差异」分开 |
| **评委产物不落盘** | 评委的 prompt/输出/事件流不保存，判定无法复核 | 每轮落盘 `output.md` / `prompt.md` / `events.json` | 判定可复核；`report` 可从原始产物重算 |
| **评委失败即丢结果** | 单轮失败可能导致整条判定丢失 | 主判定轮全失败时降级使用反向轮并标注来源 | 单轮故障不丢整条判定 |
| **汇总不可重算** | 汇总结果只在内存与数据库中，逻辑修正后无法回溯 | 新增 `recomputeSummary()`，从 `cases/` 与 `pairwise/` 原始产物重算 | 汇总逻辑修正后可重新出报告 |

另有一处属于本仓库自身的实现缺陷，已在开发中修复并补回归测试：运行 ID 形如 `<variant>-<task>-<attempt>`，其中 taskId 含连字符时（如 `simple-answer`），贪婪正则会把 taskId 截断成 `answer`。改为按已知 variantId 前缀切分。

## 来源二：agent-eval 的治理范式

来源仓库：`~/Dev/Projects/agent-eval`。

### 采纳

- **方案 / 执行 / 审核分离**的角色分离精神，以及对应披露要求。
- **证据层级声明**：明确区分静态检查、回放、真实模型运行、真实数据受控实验，不许混为一谈。
- **结论限于实际证据支持的范围**，分母明确。
- **保留全部 trial、失败、未知、阻断、成本**，不选择性重跑。
- **登记与版本管理**：项目台账、方案版本、运行编号、审核编号。
- **判据变更形成新版本，不追溯覆盖旧结论。**

### 不采纳

- agent-eval 的完整三阶段 Controller 流程**对本仓库过重**。skill 评估是单次对照实验，引入独立审核节点会显著抬高使用成本。本仓库改为：

  - 规则断言由代码判定（客观，无审核必要）
  - 成对评委由独立模型上下文执行
  - **同一助手可同时承担方案、执行与审核**，但必须在报告中如实披露这一限制，并标注结论为「诊断性」还是「验收级」

  这与 agent-eval 的「模式 B 单助手全流程」一致，遵循其独立性声明要求。

## 明确不采纳

| 来源 | 内容 | 不采纳原因 |
| --- | --- | --- |
| pi-xanthil | `skill-rewrite-gate.ts` 的受控回写（自动改 skill） | 评估工具不应写入被测对象，违反授权边界 |
| pi-xanthil | `skill-sandbox.ts` 的行为级隔离（system prompt 红线） | 已知缺陷：仅为文字约束，非运行时强制。作为参考记录，不作为本仓库的隔离保证 |
| pi-xanthil | `SkillHone` 的 Creator/Evaluator 双队 | 本仓库只做评估不做自动优化，无需双队 |
| agent-eval | 完整的 plan/execute/review 三阶段流程 | 对单次 skill 评估过重，改为报告披露制 |

## 待解决的已知问题

1. **pi 锁文件残留**：`~/.pi/agent/*.lock` 空目录会导致 pi CLI 启动失败（EEXIST）。本仓库的 `pi.ts` 默认通过 `HOME` 重定向到隔离目录运行（`--home` 选项），避免污染与争用。需要在运行前复制认证配置。
2. **评委与被评同模型**：当评委模型与被评模型相同时存在自我偏好风险。默认要求评委使用不同模型，或在报告中标注该风险。
3. **断言的区分度**：目前无法自动检测「几乎必然通过的断言」。计划加入断言区分度自检（对比 baseline 通过率）。
4. **成本可见性**：需要在报告首屏显示单次运行与整套评估的成本估算，避免意外超支。

## 演进方向

- 支持 `retrievalMode`：不显式指定 skill，改为让 pi 自动检索命中，测量真实检索场景下的表现。
- 支持覆盖缺口分析：把低分任务聚类，反推缺失的 skill 能力域。
- 支持 EFC 作为同分时的次级排序指标。
