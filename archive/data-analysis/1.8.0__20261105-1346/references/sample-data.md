# 内建示例数据 · 连锁零售门店运营分析

> **这份数据的作用**：让你在**不准备任何文件**的情况下，先看清产出长什么样。
> 对技能说一句「**用示例数据试一下**」，技能会直接按本文数据输出完整六段报告，你只需判断格式是否合用，再决定是否换成自己的数据。
>
> 本文数字与 `examples.md` 示例 1 的报告**逐项对应**，报告里的每个结论都能在这里复算出来。

## 六、复算校验：四步，建议先自己算一遍

这四步是技能判断「数据能不能用」的标准动作，也是你验证报告结论的入口。

### 第 1 步：乘法闭合

```
2025H1：1,250,000 人次 × 80.00 元 = 100,000,000 元  ✓
2026H1：1,112,500 人次 × 84.49 元 = 93,995,125 元  ✓
```

逐店校验 `销售额 = 客流 × 客单价`，42 家最大误差 0 元（客单价保留 2 位小数后回乘，四舍五入误差 ≤ 0.5 元/店）。

### 第 2 步：三项同比

```
销售额：93,995,125 ÷ 100,000,000 − 1 = −6.00%
客流  ：1,112,500 ÷ 1,250,000 − 1     = −11.00%
客单价：84.49 ÷ 80.00 − 1             = +5.61%
```

交叉验证：`0.89 × 1.0561 = 0.93995`，即 **−6.01%**，与 −6.00% 的差额 0.01 个百分点，来自客单价四舍五入。

### 第 3 步：增量拆解（这一步是六段契约第四段的核心）

```
总变动 = 2026H1 − 2025H1 = 93,995,125 − 100,000,000 = −6,004,875 元

客流效应   = (1,112,500 − 1,250,000) × 80.00      = −11,000,000 元
客单价效应 = (84.49 − 80.00) × 1,112,500           = +4,995,125 元

合计校验：−11,000,000 + 4,995,125 = −6,004,875 元  ✓ 与总变动完全一致（误差 0）
```

换算为占基期的百分点：客流 −11.00 个百分点，客单价 +5.00 个百分点，合计 −6.00 个百分点。

> **结论方向**：销售额下滑全部来自客流，客单价上升只抵消了一半左右。这就是示例报告判定「主因是客流而非定价」的计算依据。

### 第 4 步：异常判定（IQR 法）

客流同比为偏态分布（42 家全部为负或接近零），不适用 3σ，选 IQR 法：

```
Q1 = −12.95%  Q3 = −8.38%  IQR = 4.57 个百分点
下界 = Q1 − 1.5 × IQR = −19.81%
```

低于下界的门店 **3 家**：

| 门店 | 客流同比 | 销售额同比 | 客单价变化 | 判定 |
|---|---:|---:|---:|---|
| 直营-01 | −24.0% | −19.2% | 80.00 → 85.03 | 越界 |
| 直营-02 | −22.0% | −15.0% | 80.00 → 87.14 | 越界 |
| 直营-03 | −21.0% | −14.3% | 80.00 → 86.75 | 越界 |

这三家的共同特征：客流掉得多，但客单价反而明显上升（85~87.2 元，高于整体 84.49 元），说明留下的是高客单客群，属于「客流结构性流失」而非「整体消费降级」。

> 注意：这三家**不是录入错误**——连续 23 天低于阈值（直营-01，5 月 12 日至 6 月 3 日），属真实业务波动，应列入异常清单而非删除。

## 七、脏数据对照集（体检用）

上面三~六节是**干净数据**，用它只能证明「算得对」。这一节是**故意做坏的同一份业务**，用来证明技能「能抓错」。

真实工作里的表极少是干净的。**客户拿自己的表跑一遍，结果通常不如样例漂亮——多数时候不是技能不行，是表本身有问题。** 先跑体检把问题指出来，比直接出报告更有价值。

对技能说一句「**体检一下我的表**」，或直接跑：

```bash
python scripts/quality_check.py --data references/dirty-sample.csv --key 门店,月份
```

> 主键要写全。只写 `--key 门店` 会报「9 行 / 4 个唯一值」——那是因为同一门店跨了多个月，属于误报。月度面板的主键是 **门店 + 月份**。

**这六项未通过里哪一项最致命**：DT03。合计行说 91,140，明细加总 136,833，差 45,693 人次。若直接拿合计行做同比，报告第一段的数字就是错的，后面拆解得越精细，错得越远。

**为什么 DT06 判「通过」**：各期记录数都是 3 条，行数一致；日历天数虽不等（31/31/30），但只有行数与天数**同时**不等才判为不可比。这样做是为了避免把「每月一条汇总」的正常表误伤。

### 7.4 逐项怎么处置

| 检查 | 处置动作 | 禁止做法 |
|---|---|---|
| DT01 重复行 | 按「门店 × 月份」去重，记录剔除条数 | 直接删行不留痕，事后无法复算 |
| DT02 主键重复 | 确认是一对多还是多对多；多对多须先聚合到同粒度再连接 | 用 `COUNT(*)` 计数，会放大 |
| DT03 合计不符 | 以明细加总为准，合计行重算或标注作废 | 沿用原合计行，只改说明 |
| DT05 时间缺口 | 标注该期缺失、不插补，同比时注明 | 用前后期均值填充缺口 |
| DT06 天数不等 | 换算日均或按同天数对齐后再比总量 | 直接比月度总量，2 月天然偏低 |
| E 口径变更 | 并列新旧两套口径结果，或回溯重算旧期间 | 把口径变更当业务增长汇报 |

### 7.5 关于 E：脚本判不出来的那一类

口径变更无法从数据本身看出来——数字都是合法的，只是含义变了。所以 SKILL.md 把它写成红线 9（禁止分母变更后直接比），靠**读口径说明 + 主动追问**发现，而不是靠脚本。

这也是「首次接触新数据源先问五件事」的由来：⑤ 新人最容易在哪一步算错，问的就是这一类。

## 八、换成你自己的数据

两种方式，任选其一：

**方式一（最省事）**：直接说「照这个格式，我把自己的表贴给你」，把表 A、表 B 按上面列名贴进来即可，缺列技能会提示补。

**方式二（推荐，能跑得更准）**：按下面的映射表整理成 CSV/表格，字段名可不同，但要能对上。

| 本文字段 | 你数据里可能的叫法 | 是否必填 | 缺失后果 |
|---|---|---|---|
| 月份 / 日期 | 统计月、账期、period | 必填 | 无法做趋势与同环比 |
| 销售额 | 营收、GMV、净成交额、revenue | 必填 | 无法拆解 |
| 客流 | 进店人次、UV、访问量、traffic | 选填 | 无法做客流×客单价拆解，只能做单因子 |
| 客单价 | 平均单价、ATV、AOV | 选填 | 可由销售额÷客流自动算 |
| 门店 / 分组 | 区域、渠道、品类、sku | 选填 | 无法做分组对比与异常定位 |
| 退货额 / 优惠额 | 退款、折扣、discount | 选填 | 无法还原净成交口径，须注明是否含税含退货 |

**数据不合格时的处理**：技能不会替你猜。缺口径会标「⚠️ 输入不完整」、缺样本量会标「样本量不足，仅供参考」、有缺失值只标注不插补（插补会伪造趋势）。
