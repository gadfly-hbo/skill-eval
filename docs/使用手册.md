# 使用手册

## 0. 一次性准备

```bash
cd ~/Dev/Projects/skill-eval
npm install
npm link                 # 让 skill-eval 命令全局可用
```

### 准备 pi 隔离 HOME（重要）

pi CLI 会在 `~/.pi/agent/` 下建锁文件，多个进程并发时会争用导致启动失败。
评估时用隔离 HOME，既避锁又不会污染你的全局 pi 配置。

用仓库自带的脚本（可重复执行，会顺手清掉上次残留的锁目录）：

```bash
bash ~/Dev/Projects/skill-eval/scripts/setup-pi-home.sh
```

脚本默认建在 `~/.skill-eval/pi-home`，也可以指定别的路径：

```bash
bash ~/Dev/Projects/skill-eval/scripts/setup-pi-home.sh /path/to/pi-home
```

手动等价做法：

```bash
mkdir -p ~/.skill-eval/pi-home/.pi/agent
cp ~/.pi/agent/{auth.json,models-store.json,models.json} ~/.skill-eval/pi-home/.pi/agent/
chmod 600 ~/.skill-eval/pi-home/.pi/agent/auth.json
```

这一步只需做一次。注意：pi 的模型更新**不会**自动同步到隔离目录——
如果升级了 pi 或换了模型认证，需要重新执行一次脚本。

## 1. 最小可用流程（两步）

### 第 1 步：把 skill 放进待测评区

```bash
skill-eval pending --repo ~/Dev/Projects/skill-eval --init
```

然后把待测 skill 的**整个文件夹**拖进 `~/Dev/Projects/skill-eval/pending/`。

### 第 2 步：调用 skill-eval-flow

```
/skill:skill-eval-flow
```

或者直接对 agent 说「评估这个 skill」。

**完事。** 套件生成、环境自检、跑批、归档、报告解读全在流程内部完成——
你不用写套件、不用敲命令、不用指定模型。

### 第 1 步：写套件

在 `suites/` 下建一个 JSON，描述「用哪些任务测这个 skill」。

```json
{
  "id": "my-skill-eval",
  "name": "我的 skill 评估套件",
  "version": "1",
  "skill": { "path": "../examples/json-contract-skill/SKILL.md", "version": "1.0.0" },
  "repeat": 3,
  "judgeRepeat": 2,
  "tasks": [
    {
      "id": "task-1",
      "prompt": "用 JSON 回答：该不该先做灰度上线？",
      "expectedPoints": ["给出明确建议", "输出为单个 JSON 对象"],
      "assertions": [
        {
          "kind": "jsonSchema",
          "schema": {
            "type": "object",
            "required": ["answer", "confidence"],
            "properties": {
              "answer": { "type": "string" },
              "confidence": { "type": "number", "minimum": 0, "maximum": 1 }
            }
          },
          "note": "必须是含 answer 与 confidence 的 JSON 对象"
        },
        { "kind": "mustNotMatch", "pattern": "```", "note": "不得包裹代码块" }
      ]
    }
  ]
}
```

**写套件的关键**：任务要能体现 skill 声称的**行为约束**，而不是泛泛的「写点东西」。
断言要在**看结果之前**写死，否则就是自证。

先校验结构（不花钱、不调模型）：

```bash
skill-eval check --suite suites/my-suite.json
```

### 第 2 步：跑

```bash
skill-eval eval \
  --suite suites/my-suite.json \
  --skill /path/to/your/SKILL.md \
  --model minimax-cn/MiniMax-M3.1-Flash \
  --judge-model xiaomi-token-plan-cn/mimo-v2.6-flash \
  --home ~/.skill-eval/pi-home \
  --out runs/exp-001
```

`--skill` 可以省略，套件里 `skill.path` 会被使用。`--model` 必须给（或设 `SKILL_EVAL_MODEL` 环境变量）。

### 第 3 步：看报告

open runs/exp-001/REPORT.md

## 2. 怎么读报告

报告有 9 节，最该看的是**首屏结论表**、**第 6 节分歧**和**第 8 节优化建议**。

### 首屏结论表

| 指标 | 怎么读 |
| --- | --- |
| 激活率 | skill 有多大概率被模型真正读取。**低于 60% 说明 skill 描述写得不好，模型不知道什么时候该用它** |
| 胜率 | 相对 baseline 的改善比例。**只有激活率高但胜率低，说明模型读了但没用好**——skill 内容写得不好 |
| 断言通过率 | baseline vs skill 的对比。**这个比胜率更客观**，规则由代码判定 |
| 平均耗时/token | 成本。skill 让输出变慢变贵是常见代价，要权衡 |

**只有激活率和胜率都达标，结论才是「有效」。** 详见第 3 节。

### 第 6 节分歧

规则断言和评委结论不一致时列在这里。**以规则为准**，但分歧本身是重要信号：

- 规则说改善、评委说没差异 → 任务设计或 skill 声明有偏差
- 规则说没差异、评委说改善 → 断言可能不够有区分度

分歧多说明断言写得不对，需要重新设计。

### 第 5.4 节评委标签纠正记录

评委是模型，会给出**自相矛盾**的输出——标签说 A 胜，分数却说 B 高出 25 分。
工具发现这种矛盾时**以分差方向为准**并把纠正记录在这里。

这一节非空说明工具替评委做了判断，**必须读**：单条矛盾就足以翻转整轮结论
（实测：按标签 5/10 = 50% 判「结论不足」，按分差 6/10 = 60% 判「有效」）。

> 校验锚点是**分差方向**，不是提示词里「B 更好」的字面描述——
> 实测评委实际按「分数更高的那份更好」打标签。反向轮（位置偏好探测轮）
> 会先换算 A/B 口径再校验，两条路径口径统一。

### 第 7 节限制

**这一节必须读**。常见限制：

- 「评委与被评使用同一模型，自我偏好风险未消除」→ 换个评委模型重跑
- 「N 对比较未能判定」→ 有运行失败，去看对应 case 的 `result.json`
- 「检测到弱激活」→ 模型可能只是碰巧说了关键词，需要看 events.json 确认

### 第 8 节优化建议（没通过时看这里）

只有 skill **没通过**时才会出现这一节，按四种失败模式归类给出可执行方向：

| 失败模式 | 含义 | 优化方向 |
| --- | --- | --- |
| **契约未落地** | skill 声称的约束没进输出（baseline 稳过、装了 skill 反而失败） | 把约束从「描述」改成「可执行的硬性步骤或模板」 |
| **契约无效** | 装了 skill 也没满足（两侧都没过） | 约束可能超出模型能力，或表述本身有歧义 |
| **约束不稳** | 同一条断言时过时不过 | 加强约束强度，或拆成多条独立断言 |
| **未触发** | 模型压根没读 skill | 改 frontmatter description，写清「什么时候该用」 |

**关键归因原则**：baseline 本来就能过的断言**不算 skill 的问题**，不会列进建议——
否则优化建议会把你引向与 skill 无关的地方。

「下一步」小节会给出二次测评的准备要求：改完 skill 后**保持同一套件与模型**，
只改 skill 内容，否则无法归因。

## 3. 结论怎么判

工具自动判定规则：

| 激活率 | 胜率 | 结论 | 含义 |
| --- | --- | --- | --- |
| ≥60% | ≥60% | **有效** | 触发稳定且有实质提升 |
| ≥60% | <60% | **结论不足** | 触发了但没变好，skill 内容有问题 |
| <60% | 任意 | **无效** | 模型基本不用它 |
| 0% | 0% | **无效** | 完全没被触发 |

### 三种典型的「无效」及对策

| 症状 | 根因 | 对策 |
| --- | --- | --- |
| 激活率低（<30%） | skill 的 `description` 没写清「什么时候用」 | 改写 description，写触发场景而不是写功能 |
| 激活率高、胜率低 | skill 内容太啰嗦/太抽象，模型读了也不知道怎么做 | 把 skill 写成可执行的步骤与具体约束 |
| 断言通过但胜率低 | skill 约束太弱，模型本来就做对了 | skill 没有增量价值，考虑删掉 |

### 判定必须用增益，不能用绝对通过率

本工具实测发现：**断言整体灵敏度只有 51.9%**（27 条断言中 13 条 baseline 不装 skill 也能全过）。这意味着：

- 断言通过率虚高——skill 完全无效时，绝对通过率仍可达 75.9%
- 增益被稀释——真实增益 +50pp 会被摊到含大量「白送断言」的分母上

所以判定看的是 **baseline → variant 的差值**，不是 variant 的绝对值。表里的「断言通过率」只用于观察，绝对不要单独拿它下结论。

### 阴性对照：自查工具可信度（标准动作）

拿到一个「某 skill 有效」的结论，怎么知道工具本身不是在对任何输入都给高分？做**阴性对照**。

**契约二分法**：Agent Skill 的文本可以二分——

| 契约类型 | 载体 | 作用 |
| --- | --- | --- |
| **触发契约** | frontmatter 的 `description` | 决定「何时该用这个 skill」 |
| **行为契约** | 正文的行为约束、输出格式、红线、流程 | 决定「用了之后该长什么样」 |

阴性对照**只剥离行为契约、保留触发契约**，重跑一遍。若断言通过率回落至 baseline 水平，说明断言确实在度量 skill 契约；若仍接近原版，说明工具没有区分能力。

> 关键：破坏版必须保持高激活率。若连触发契约也剥掉了，skill 压根不激活，实验无效。

脚本已内置：

```bash
node --experimental-strip-types scripts/negative-control-compare.ts \
  --original <原版跑批目录> --broken <破坏版跑批目录>
```

判定阈值：原版增益 ≥ 10pp 且破坏版增益 < 10pp → 工具具备区分能力。

2026-11-01 的实测结果（data-analysis，M3.1-Flash / mimo-v2.6-flash，repeat=2）：

| 组别 | 断言通过率 | 增益 | 激活率 |
| --- | --- | --- | --- |
| baseline | 50.0%（29/58） | — | 0% |
| 原版 skill | 100.0%（58/58） | **+50.0 pp** | 100% |
| 破坏版 skill | 75.9%（44/58） | **+8.6 pp** | 100% |

三组单调分离、0 条假阳性。完整分析见 [experiments/negative-control-2026-11-01/阴性对照验证报告.md](../experiments/negative-control-2026-11-01/阴性对照验证报告.md)。

> 目前阴性对照只在 data-analysis 一个 skill 家族上验证过，跨家族普适性未测。

## 4. 全部命令

### eval — 执行对照评估

```bash
skill-eval eval --suite <套件.json> [选项]
```

| 选项 | 说明 |
| --- | --- |
| `--suite <path>` | 套件定义（必填） |
| `--skill <path>` | 被测 SKILL.md，覆盖套件设置 |
| `--model <id>` | 被评模型，如 `minimax-cn/MiniMax-M3.1-Flash` |
| `--judge-model <id>` | 评委模型，默认同被评模型。**建议换不同 provider 的模型**（如 `xiaomi-token-plan-cn/mimo-v2.6-flash`），避免自我偏好 |
| `--repeat <n>` | 每用例重复次数，默认取套件值或 3 |
| `--judge-repeat <n>` | 评委轮数。**≥2 才启用位置偏好探测**，建议 2~3 |
| `--out <dir>` | 输出目录，默认 `runs/<run-id>` |
| `--home <dir>` | pi 隔离 HOME |
| `--context <text>` | 附加上下文前缀（两侧一致） |
| `--no-keyword-signal` | 只用工具调用取证激活 |
| `--timeout <ms>` | 单次运行超时，默认 480000 |
| `--judge-timeout <ms>` | 评委单次超时，默认 300000。评委要在两份长输出之间比较，思考链比被评模型更长，超时须比被评模型宽 |

### check — 只校验套件（不调模型、不花钱）

```bash
skill-eval check --suite <套件.json>
```

### report — 从已有产物重新出报告

```bash
skill-eval report --run runs/exp-001 --suite-file suites/my-suite.json
```

**加 `--suite-file` 很重要**：这样会从 `cases/` 和 `pairwise/` 原始产物重算汇总，
而不是复用旧的 `summary.json`。汇总逻辑修正后必须用这个。

**一条命令跑完直接入库**（方案 A）：

```bash
skill-eval eval --suite suites/my-suite.json --skill <SKILL.md> \
  --model <被评模型> --archive-to /path/to/repo
```

`--archive-to` 会让 eval 在生成报告后自动把通过测评的 skill 归档进该仓库。
不传这个参数时，eval 的行为与从前完全一致——**不会**碰任何仓库。

| 选项 | 说明 |
| --- | --- |
| `--archive-to <dir>` | 评估后归档到该仓库（默认归档到 `<dir>/archive`） |
| `--archive-root <dir>` | 覆盖归档根目录 |
| `--archive-version <id>` | 指定版本标识（默认 `<frontmatter版本>__<时间戳>`） |
| `--allow-inconclusive` | 允许归档「结论不足」的评估 |

**归档失败不影响评估结论**——评估本身已成功、报告已落盘，归档只是附加动作。
失败时 stderr 会说明原因，stdout 仍照常输出 verdict。

### archive — 把通过测评的 skill 存进仓库

```bash
skill-eval archive --run runs/exp-001 --repo /path/to/repo
```

把评估结论为「有效」的 skill 快照存进仓库的 `archive/` 目录，作为可回滚、可追溯的存档。

**为什么以 `--run` 为主入口**：归档必须绑定某一次评估的产物。只给 skill 路径，
无法确定它对应的 verdict 与内容哈希——归档了「某次测过的那个文件」比「这个文件」更重要。

| 选项 | 说明 |
| --- | --- |
| `--run <dir>` | 评估运行目录（必填），提供 verdict 与元信息 |
| `--skill <path>` | 被测 SKILL.md 路径，可从运行产物自动反推 |
| `--archive-root <dir>` | 归档根目录，默认 `<仓库>/archive` |
| `--repo <dir>` | 仓库根目录，用于安全校验，默认向上自动探测 |
| `--version <id>` | 显式版本标识，默认 `<frontmatter版本>__<时间戳>` |
| `--allow-inconclusive` | 放行「结论不足」的评估，默认拒绝 |
| `--allow-low-gain` | 放行断言增益未达标的评估，默认拒绝 |
| `--gain-threshold <pp>` | 增益门槛（百分点），默认 10 |
| `--force` | 忽略 verdict 强制归档（仅用于诊断） |

**归档门控（三道关）**：

| 关卡 | 条件 | 放行方式 |
| --- | --- | --- |
| 结论 | `effective` | 直接放行 |
| 结论 | `inconclusive` | `--allow-inconclusive`，归档后标 `provisional=true` |
| 结论 | `ineffective` | **永不放行**（`--force` 仅供诊断） |
| **增益** | 断言增益 ≥ 10pp | 直接放行 |
| **增益** | 断言增益 < 10pp | `--allow-low-gain`，归档后标 `lowGain=true` |
| **增益** | 增益不可判定 | 视为不达标（证据不足不能默认放行） |

**为什么光有「有效」结论还不够**：阴性对照实验证明断言整体灵敏度只有 51.9%——
27 条断言中 13 条 baseline 不装 skill 也能全过。这意味着：

- skill 完全无效时，断言通过率仍可达 75.9%
- 一个 `effective` 结论里可能混着大量「模型本来就能做对」的白送断言

所以归档要看**增益**（baseline → skill 的差值），10pp 门槛来自阴性对照实验的判定线
（原版 +50.0pp，契约剥离后 +8.6pp，恰好能区分「真契约有效」与「模型自发守纪律」）。

**产出结构**：

```text
archive/<skill名>/
├── <版本标识>/            # 如 1.8.0__20261103-2303
│   ├── SKILL.md           # skill 本体快照
│   ├── references/        # 附属文件一并复制——缺了 skill 跑不起来
│   ├── scripts/
│   ├── ARCHIVE.md         # 元信息卡：哈希、模型、结论、增益门槛、复现命令
│   └── REPORT.md          # 评估报告副本，使归档目录自包含
└── latest.json            # 当前版本指针（含 gainPp / lowGain / provisional）
```

**几条硬规则**：

- 归档目标**不得**落在 `skills/` 下——那里会被 pi / Claude Code / Codex 自动扫描，
  归档内容进入后会污染后续评估，命令会直接报错拒绝。
- **幂等**：内容哈希相同则跳过，不产生重复归档。
- **不覆盖**：同版本不同内容会另起 `-r2`、`-r3` 目录，原版本保留。
- **只读**：绝不修改被测 skill。
- **不自动 commit**：由你决定何时提交。
- 归档成功后会**自动从待测评区移出**该 skill（暂存区清空则目录删除），
  没通过的 skill 留在暂存区等二次测评。

### pending — 待测评暂存区（候选池）

```bash
# 登记：把未测的 skill 放进暂存区
skill-eval pending --repo /path/to/repo --skill ~/.workbuddy/skills/my-skill/SKILL.md

# 只把目录建出来，然后你自己把 skill 文件夹拖进去
skill-eval pending --repo /path/to/repo --init

# 列出：看暂存区里有哪些 skill
skill-eval pending --repo /path/to/repo

# 列出（JSON，给 agent 解析用）
skill-eval pending --repo /path/to/repo --json
```

暂存区默认在 `<仓库>/pending/`，语义是**常驻的投放入口**：

> **`pending/` 是常驻目录，建好就一直留着。**
> 你可以直接把待测评的 skill 文件夹**拖进去**，不必先敲命令登记。
> 测评通过的 skill 会从这个文件夹里移走（进 `archive/`），但**文件夹本身保留**，
> 你随时可以往里放新的。

**仓库根不用指定**：CLI 会依次尝试 `SKILL_EVAL_REPO` 环境变量 →
当前目录向上探测 → 从 skill-eval 自身安装位置反推。
所以从任何目录发起都能落到 skill-eval 仓库的待测评区。

评估**其他项目**的 skill 时，才需要显式指定：

```bash
# 评估某个项目里的 skill —— 待测队列和归档都在那个项目里
skill-eval pending --repo ~/Projects/my-project --skill ~/.workbuddy/skills/my-skill/SKILL.md
# → ~/Projects/my-project/pending/my-skill/
```

也可以用 `--pending-root <dir>` 完全自定义位置。

| 行为 | 说明 |
| --- | --- |
| **常驻存在** | 任何一次 `pending` 调用都会确保目录存在；`--init` 只建目录不做别的 |
| **可直接拖入** | 拖进来的 skill 文件夹会被自动识别（看有没有 `SKILL.md`），并补写登记信息，来源标为「（手动投放）」 |
| 登记是**复制** | 用 `--skill` 登记时是复制而非移动——源 skill 通常在 agent 自动扫描位置，不能被搬走 |
| 归档成功自动移出 | `archive` / `eval --archive-to` 成功后，已归档的 skill 从暂存区移走 |
| **文件夹本身保留** | 移出后目录仍在，可以继续放新的待测 skill |
| **未通过的刻意留下** | 没通过的 skill 留在暂存区等二次测评，这是正常行为不是 bug |

每次登记会写一份 `.pending-meta.json` 记录来源路径与登记时间（来源路径已脱敏）。
这个元信息文件是隐藏文件（`.` 开头），`ls` 看不到，用 `ls -a`。

**`--json` 输出**：给 agent 自动发现用，结构是

```json
{
  "pendingRoot": "/path/to/repo/pending",
  "exists": true,
  "skills": [
    {
      "name": "my-skill",
      "skillPath": "/path/to/repo/pending/my-skill/SKILL.md",
      "source": "（手动投放）",
      "registeredAt": "2026-11-04T02:58:29.606Z"
    }
  ]
}
```

`skillPath` 直接就是 `--skill` 参数要的值。

## 5. 断言类型速查

| kind | 必填字段 | 用途 |
| --- | --- | --- |
| `mustMatch` | `pattern` | 必须匹配某正则 |
| `mustNotMatch` | `pattern` | 必须不匹配（**最有区分度**） |
| `mustContain` | `value` | 必须包含某字符串 |
| `mustNotContain` | `value` | 禁止出现某字符串（如套话） |
| `jsonSchema` | `schema` | 输出必须是符合 schema 的 JSON |
| `numeric` | `pattern`, `expected` | 数值断言，可加 `tolerance` |

`numeric` 的 `pattern` 必须含一个捕获组：

```json
{ "kind": "numeric", "pattern": "置信度\\s*([0-9.]+)", "expected": 0.85, "tolerance": 0.05 }
```

`jsonSchema` 支持的关键字：`type`、`required`、`properties`、`enum`、`minimum`、
`maximum`、`minLength`、`maxLength`、`items`、`minItems`。

### 5.1 `equivalentPatterns`：区分「断言过严」与「skill 真缺陷」

`mustMatch` / `mustNotMatch` 可选字段 `equivalentPatterns`——
声明「契约语义的**其他合规写法**」（主 `pattern` 之外的等价表达）。

```json
{
  "kind": "mustMatch",
  "pattern": "责任人|负责人",
  "equivalentPatterns": ["谁做", "谁负责"],
  "note": "红线 5：建议必须落到责任人"
}
```

**为什么需要它**：断言失败有两种完全不同的性质，而它们在「两侧逐次通过与否」的
布尔数据里**完全无法区分**——实测两条假失败与一条真缺陷的签名都是
`baseline ✗✗ / skill ✓✗`。区别只在输出文本里：

| 情况 | 判定 | 要改什么 |
| --- | --- | --- |
| 失败且命中了某个 `equivalentPatterns` | **断言过严**（假失败） | **套件**：放宽 pattern |
| 失败且等价写法都没命中 | 真缺陷 | **skill**：改 SKILL.md |
| 失败但没声明 `equivalentPatterns` | 无法区分 | 按原逻辑归类 |

报告第 8.3 节会单独列出「断言过严」的条目，避免让用户去改本来正确的地方。

> `equivalentPatterns` 是**兜底**——`pattern` 已放宽到位时它就不再必需；
> 但保留它能让「pattern 漏了某种措辞」被识别成假失败，而不是误判成 skill 缺陷。

```text
runs/exp-001/

│   │   └── result.json                        激活取证 + 断言判定

    ├── forward/                               正向评判
    │   ├── output.md                          评委输出
    │   ├── prompt.md                          评委提示词
    │   └── events.json

**排查问题的顺序**：

1. 报告第 7 节说哪次运行失败 → 打开对应 `result.json` 看 `stderr`
2. 想知道模型有没有读 skill → 打开 `events.json` 搜 `tool_execution_start` 里有没有 skill 路径
3. 想知道模型读了但用得不好 → 对比 `cases/baseline/` 和 `cases/skill/` 的 `output.md`
4. 想知道评委为什么这么判 → 打开 `pairwise/*/forward/prompt.md` 和 `output.md`

## 7. 成本与耗时参考

实测（`minimax-cn/MiniMax-M2.7`，3 用例 × 2 变体 × 2 重复 = 12 次运行 + 12 次评判）：

- 耗时：约 3.5~6 分钟
- 成本：约 $0.03
- token：约 16 万

**估算公式**：运行次数 = 用例数 × 变体数 × repeat；评委调用次数 ≈ 运行次数 × judgeRepeat × 2。

想要快一点：`--repeat 1 --judge-repeat 1`（约 1/4 成本，但结论稳定性下降）。
想要结论可靠：`--repeat 3 --judge-repeat 3`。

## 8. 常见问题

**Q: pi 报 `EEXIST: file already exists, mkdir '.../auth.json.lock'`**
没配 `--home`，或隔离 HOME 没建好。见第 0 节。
如果隔离 HOME 是从别的路径迁移过来的，旧目录里可能残留了空的 `*.lock` 目录，
重跑一次 `scripts/setup-pi-home.sh` 会清掉。

**Q: 所有用例都在 1 秒内 failed，stderr 报 `[safe-delete] broker denied delete` 或 `EEXIST ... trust.json.lock`**
你在 IDE（CodeBuddy / WorkBuddy）里跑这个工具，且 pi 隔离 HOME 不在临时目录下。
宿主 IDE 会给所有 node 子进程注入文件系统 hook，pi 维护自己锁目录的 `mkdir`/`rmdir`
会被拦截并让 pi 崩溃。

本工具已在 `src/core/pi.ts` 里自动处理：spawn pi 前会剥离宿主注入的 hook，
**正常情况下你不会看到这个错误**。如果仍遇到，说明你的宿主用了别的注入方式，
请把 stderr 里的报错贴出来。

**Q: 激活率 0%，但模型回答得很好**
skill 的 `description` 没写清触发条件。改 description，写「什么时候该用」而不是「这是什么」。

**Q: 胜率上下波动很大**
`--repeat` 太小。提到 3 以上。`--judge-repeat 1` 时评委单次判定噪声也大，提到 2。

**Q: 报告说「结论不足」**
只满足一个条件。要么激活率不够（skill 没被充分触发），要么胜率不够（读了没用好）。看第 4 节的对照表判断。

**Q: 想评估非 pi 的 skill（Claude Code / Codex 的 skill）**
当前内核基于 pi CLI。核心方法（对照实验、激活取证、成对评委、断言）是通用的，
换运行层需要实现 `src/core/pi.ts` 的接口。

**Q: 能同时评多个 skill 吗**
当前一次评一个。多个 skill 的对比可以做成多个 variant，需要扩展 runner 的 variant 定义。
